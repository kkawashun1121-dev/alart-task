## 2. iOS でどうやって「止まらないアラーム」を作るか

### 結論: 二重系で組む

iOS には Android の `AlarmManager` に相当するものが無い。
そこで **主系と副系の2本立て**にする。純正時計アプリ以外のアラームアプリ（Alarmy 等）も同じ手法。

```
┌─ 主系: キープアライブ方式（本命・確実） ───────────────┐
│ 就寝時に「アラームをセット」した瞬間から、             │
│ 無音の音声を延々とループ再生してアプリを生かし続ける   │
│   → iOS はオーディオ再生中のアプリを殺さない          │
│   → 起床時刻に JS タイマーが動き、爆音に切り替える     │
│   → playsInSilentMode: true で消音スイッチも無視       │
│   → タスク完了まで永久に鳴り続ける（30秒制限なし）     │
└────────────────────────────────────────────────────┘
┌─ 副系: ローカル通知の連打（保険） ─────────────────┐
│ 主系がOSに殺された場合に備え、就寝時に               │
│ 起床時刻から1分間隔で通知を60個スケジュールしておく   │
│   → 1個あたり音は30秒だが、1分ごとに鳴り直す          │
│   → これが「タスクをやらないとすぐスヌーズが出る」の実体│
│   → タスク完了時に残りを全キャンセル                 │
└────────────────────────────────────────────────────┘
```

### 主系の技術的裏付け

`expo-audio` の設定でこう書ける:

```ts
setAudioModeAsync({
  playsInSilentMode: true,      // ← 消音スイッチを無視して鳴る
  shouldPlayInBackground: true, // ← アプリを閉じても鳴り続ける
  interruptionMode: 'doNotMix',
})
```

`app.json` の config plugin が `UIBackgroundModes: ["audio"]` を自動で入れてくれる。

**代償**: 就寝中ずっとオーディオセッションが動くのでバッテリーを食う。
→ **充電しながら寝る運用が前提**。これは目覚まし時計として自然なので問題なし。

### 副系（通知連打）の制約

| 制約 | 内容 | 対処 |
|---|---|---|
| 保留通知の上限 | iOSは **64個**まで | 1分間隔 × 60個 = 60分ぶんで十分 |
| 1通知の音の長さ | **最長30秒** | 連打でカバー |
| 集中モード/おやすみモード | 通常は届かない | `interruptionLevel: 'timeSensitive'` で突破。**これは自分で有効化できる**（Critical Alerts と違い Apple の承認不要） |
| 消音スイッチ | 通知音は鳴らない | 主系のアプリ内オーディオがカバー |

> **Critical Alerts は不要**。あれは Apple の個別承認が必要で個人開発では通らないが、
> 「Time Sensitive」なら Developer アカウントの設定画面で自分でオンにできる。

## 3. Windows から iPhone にアプリを入れる方法

ここが一番の障壁。整理すると:

| 方法 | Mac | 費用 | 有効期限 | 判定 |
|---|---|---|---|---|
| **EAS Build + Ad Hoc配布** | **不要** | **$99/年** | 1年 | ◎ **これ一択** |
| EAS Build + TestFlight内部テスト | 不要 | $99/年 | 90日ごと再ビルド | ○ 審査不要だが期限が短い |
| Xcode + 無料Personal Team | **必要** | 無料 | 7日ごと再署名 | × Macが要る |
| PWA（ホーム画面に追加） | 不要 | 無料 | — | × アラームとして成立しない |

### 推奨フロー

```
Windows PC で コードを書く
   ↓
eas build --platform ios --profile preview
   ↓（Expoのクラウド上のMacがビルドしてくれる）
ビルド完了 → QRコードが出る
   ↓
iPhone でQRを読む → その場でインストール
```

`eas.json` の設定:
```json
{
  "build": {
    "preview": {
      "distribution": "internal",
      "ios": { "simulator": false }
    }
  }
}
```

初回に自分のiPhoneのUDIDを登録する（`eas device:create` がQRコードを出してくれる）。以降は不要。

### 費用について

**Apple Developer Program の年 $99（約15,000円）は避けられません。**
Mac無しでiPhoneに自作アプリを入れる唯一の合法的な道です。

これが許容できない場合の選択肢は2つ:
1. 中古のMac miniを買う（$99/年より安く済む可能性がある）
2. まずPWAで作り、価値を確認してからネイティブに移行する

→ **Phase 0 として、まずPWAでタスク部分だけ試すのを強く勧めます。**
「日付を撮影して起きる」が自分に本当に効くかを、1円もかけずに検証できます。

## 4. 技術スタック（**相談中** — ここが最大の分岐点）

### 判断の軸

このアプリの技術選定は、以下の**たった1つの問い**でほぼ決まる。

> **就寝中、アプリが裏に回っている状態で、指定時刻に確実に音を出せるか？**

UIの書きやすさも、学習コストも、この問いの前では二次的。
鳴らなかったら目覚ましとして無価値だから。

### 候補A: Expo (React Native) + TypeScript

```
Expo SDK 56
├─ expo-audio                          … 無音キープアライブ＋爆音再生
├─ expo-notifications                  … 通知連打（副系）
├─ react-native-vision-camera          … カメラ
├─ react-native-vision-camera-ocr-plus … オンデバイスOCR（ML Kit）
├─ expo-sqlite / MMKV                  … ログ保存
└─ EAS Build                           … Windowsからクラウドビルド
```

**良い点**
- **TypeScript / React の既存スキルがそのまま使える**（travel-planner の経験が活きる）
- **EAS Build が Windows→iOS ビルドの体験として最も整っている**。コマンド1つでQRコードまで出る
- `expo-audio` が `playsInSilentMode` / `shouldPlayInBackground` を公式サポート。消音スイッチ突破は確実にできる
- 通知・カメラ・OCR・保存のライブラリが全部揃っていて、繋ぐだけで動く
- 画面のUIを速く作れる。カレンダー画面などは圧倒的に楽

**悪い点（正直に）**
- ⚠️ **最大の懸念: バックグラウンドでの JS タイマーの信頼性**。
  オーディオ再生でアプリのプロセスは生き残るが、その間 JavaScript スレッドが
  1秒ごとに確実に回り続ける保証は Expo の公式ドキュメントにはない。
  「たぶん動く」は目覚ましでは許容できない。**実装して数日試すまで確証が持てない**
- Expo Go では動かない。`prebuild` + Dev Client 必須で、ビルド1回に10〜20分かかる
- 音まわりを本気でチューニングしようとすると、結局 Swift でネイティブモジュールを書く羽目になる可能性
- OCRライブラリが個人メンテのフォークで、長期のメンテ性に不安が残る

### 候補B: Flutter + alarm パッケージ

```
Flutter
├─ alarm (gdelataillade/alarm)     … iOSでアラームを鳴らすことに特化したパッケージ
├─ google_mlkit_text_recognition   … オンデバイスOCR（日本語対応）
├─ camera                          … カメラ
├─ drift / sqflite                 … ログ保存
└─ Codemagic                       … Windowsからクラウドビルド
```

**良い点**
- ⚠️ **決定的な差: `alarm` パッケージは iOS ネイティブ側（AVAudioPlayer）で再生をスケジュールする**。
  Dart のコードが止まっていても音は鳴る。候補Aの最大の懸念が構造的に存在しない
- このパッケージは「iOSで目覚ましを作る」という、まさに今回の目的のためだけに存在する。
  消音スイッチ突破・バックグラウンド維持・端末再起動対応が最初から入っている
- Dart は AOT コンパイルされ、バックグラウンド isolate の扱いが RN より素直
- ML Kit の公式ラッパーがあり、OCR のメンテ性も良い

**悪い点**
- **Dart / Flutter を新規に学ぶ必要がある**（React経験者なら1〜2週間で書けるようになるが、ゼロではない）
- Windows→iOS のクラウドビルドは Codemagic 等を自分で設定する必要があり、EAS より手間
- 既存の TypeScript 資産・知識が使えない
- UIの書き味は好みが分かれる（ネストが深くなりがち）

### 候補C: PWA（Phase 0 用）

**良い点**: 無料・即日・Windowsだけで完結・スキルそのまま
**悪い点**: **アラームとして成立しない**（バックグラウンドで正確な時刻に発火する手段が Web に無い）

→ 本番には使えないが、**「日付撮影タスクが自分に効くか」の検証には最適**

### 候補D: Swift ネイティブ

**Mac が必須**なので、Windows 環境では選択肢から外れる。

---

### トレードオフの本質

| | 候補A: Expo | 候補B: Flutter |
|---|---|---|
| **鳴る確実性** | △ やってみないと分からない | ◎ 構造的に保証される |
| **学習コスト** | ◎ ほぼゼロ | △ 1〜2週間 |
| **開発速度** | ◎ | ○ |
| **ビルド環境** | ◎ EASが楽 | ○ Codemagic設定が要る |
| **失敗したときの損失** | 作り込んだ後に「鳴らない」と判明するリスク | 学習期間が無駄になるリスク |

> **要するに**: 「慣れた道具で作って、動かなかったら詰む」か
> 「新しい道具を覚えて、確実に動くものを作る」か、の選択。

### 折衷案（もし決めきれないなら）

**まず候補Aで「鳴るかどうか」だけを1〜2日で検証する**。
UIもOCRも作らず、「時刻をセット→裏に回す→数時間後に鳴るか」だけを試すアプリを作る。

- 鳴った → そのまま候補Aで進める。学習コストゼロで済む
- 鳴らなかった → 候補Bに切り替える。失った時間は2日だけ

この検証は費用 $99 を払う前にはできない（実機に入れる必要があるため）が、
**$99 を払う価値があるかの判断材料としては最も確実**。

## 5. 解除タスクの設計（日付撮影）

### 判定ロジック
1. カメラで撮影（**フォトライブラリからの選択は禁止**＝過去の写真で偽装できないように）
2. OCRで画像内の全テキストを取得
3. テキストから日付らしき文字列を全部抽出
4. **1つでも今日の日付と一致すれば解除成功**

### 対応する日付フォーマット
レシートの表記ゆれが激しいので、幅広く拾う:
```
2026年8月8日 / 2026年08月08日
2026/8/8 / 2026/08/08 / 2026-08-08 / 2026.08.08
26/08/08
令和8年8月8日 / R8.8.8
8月8日      ← 年なし。実用性を優先して許容
```

### 運用上の懸念と対策

> **「毎日レシートが手に入るとは限らない」** — これが最大の運用リスク。

日付が写っていれば何でもOKにすることで解決する。撮影対象の候補:
- レシート（前日の買い物のものでも、日付が今日なら…とはならないので注意）
- **新聞**（毎日確実に日付が変わる。最強）
- **PCやテレビの画面**（日付表示。ただしベッドから見えない場所に置くこと）
- **手書きのメモ**（前夜に自分で今日の日付を書いて洗面所に貼る）
- 電子レンジ・炊飯器・体重計などの日付表示

> **推奨は「前夜に紙に今日の日付を手書きして洗面所に貼る」**。
> 準備が就寝前の儀式になり、かつ朝は必ず洗面所まで歩かされる。入手性の問題も起きない。

### 偽装対策（自分専用なのでほどほどに）
- カメラのライブ撮影のみ許可（ライブラリ選択なし）
- スマホ画面に日付を表示して自撮り、は防げない → **防がない**。ログに残るので自分に嘘はつけない
- 「ずるをした」ボタンを用意して自己申告できるようにするのも一案

## 6. 画面構成

```
[ホーム] アラーム一覧・ON/OFF・「今夜のアラームをセット」ボタン
   ↓ 就寝時にセット
[待機] 無音キープアライブ中。「セット済み 6:30」大きく表示。画面は暗くする
   ↓ 起床時刻
[アラーム] 爆音+バイブ。時刻とスヌーズ回数を大きく表示。「タスクを開始」のみ
   ↓
[カメラ] 撮影 → OCR判定 → 失敗なら理由を出して再撮影（音は鳴りっぱなし）
   ↓ 成功
[結果] 「起床成功！ スヌーズ 3回 / 所要 12分」
   ↓
[カレンダー] 月表示。日ごとにスヌーズ回数を色で表示。統計
```

### スヌーズ回数のカウント方法

リスナーで数えるのではなく、**時刻から逆算する**のが確実:

```ts
snoozeCount = Math.floor((完了時刻 - アラーム時刻) / スヌーズ間隔)
```

アプリがバックグラウンドで殺されていてもカウントがズレない。

## 7. 実装の優先順位

| 順 | やること | 理由 |
|---|---|---|
| 1 | **主系アラーム**（無音キープアライブ→爆音） | ここが動かなければ何も始まらない。最大のリスク |
| 2 | OCR日付判定 | 単体で試せる。楽しい部分 |
| 3 | この2つを繋ぐ最小フロー | ここで一度、実際に朝使ってみる |
| 4 | 副系（通知連打） | 保険なので後回しでよい |
| 5 | ログ保存とカレンダー画面 | 動くようになってから |

> **1と2ができた時点で一度実戦投入すること。** カレンダーを先に作らない。
