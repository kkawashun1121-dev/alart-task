# タスク解除型アラーム — 要件定義（たたき台 v0.1）

作成日: 2026-08-08 / ステータス: **論点確認中**

---

## 1. 目的とゴール

### 解きたい課題
- 朝、アラームを無意識に止めて二度寝してしまう
- スヌーズを繰り返して起床時刻が後ろ倒しになる

### プロダクトの一言説明
> アラームは「止める」ものではなく「**解除条件を満たす**」もの。
> 寝ぼけたままでは物理的に達成できないタスクを課すことで、脳と体を強制的に覚醒させる。

### 成功指標（KPI 候補）
| 指標 | 定義 | 目標 |
|---|---|---|
| 一発起床率 | スヌーズ0回で解除できた日の割合 | 70%以上 |
| 再入眠率 | 解除後30分以内に再びアラームを設定/寝落ちした割合 | 10%以下 |
| 解除所要時間 | 発火からタスク完了までの秒数 | 中央値 60〜120秒 |
| 継続率 | 7日連続で使い続けた割合 | — |

> 「アラームが鳴った」ではなく「**ベッドから出た**」を成功と定義する。

---

## 2. コアコンセプト（設計の背骨）

1. **停止 = タスク完了** … 停止ボタンは存在しない。タスクを完了して初めて音が止まる。
2. **スヌーズは特権** … デフォルト無効。有効にする場合も「回数制限」「1回ごとにタスクが重くなる」など代償を課す。
3. **逃げ道を塞ぐ** … アプリを閉じる・音量を下げる・ホームに戻る、で止まらない。
4. **物理的な移動を促す** … 画面操作だけで完結するタスクは、ベッドの中で解けてしまう。→ NFC/QR/歩数が最強。
5. **前夜の自分 vs 朝の自分** … 設定変更は前夜の自分にしかできない（朝はアラーム設定を編集不可にする「ロック機能」）。

---

## 3. ユーザーストーリー

- **前夜**: 起床時刻・曜日・解除タスクの種類と難易度を設定して就寝する
- **発火**: 設定時刻に全画面のアラーム画面が起動、音+バイブ。停止ボタンはない
- **解除**: タスク画面が表示され、完了すると音が止まる
- **失敗/中断**: 途中でアプリを離れると、数秒後に再び前面に戻り鳴り続ける
- **事後**: 起床ログが記録され、連続記録（ストリーク）や統計が見られる

## 4. 機能要件

### 4.1 MVP（これが無いと成立しない）

| ID | 機能 | 詳細 |
|---|---|---|
| F-01 | アラーム登録 | 時刻・繰り返し曜日・ラベル・ON/OFF・複数登録 |
| F-02 | アラーム発火 | 端末がスリープ/画面ロック中でも全画面で起動、音+バイブ |
| F-03 | 音量制御 | 発火時にアラーム音量を強制的に上げる（or 下げられない） |
| F-04 | 解除タスク | 最低1種類。完了するまで鳴り続ける |
| F-05 | 離脱ブロック | ホームボタン/戻る/タスクキルへの耐性 |
| F-06 | スヌーズ制御 | 完全禁止 or 回数制限つき（設定で切替） |
| F-07 | 起床ログ | 発火時刻・解除時刻・スヌーズ回数・所要時間を記録 |

### 4.2 解除タスクの候補（★は二度寝防止効果が高い）

| タスク | 内容 | 覚醒効果 | 実装難度 | 備考 |
|---|---|---|---|---|
| ★ NFCタグ | 洗面所/冷蔵庫/トイレに貼ったタグにかざす | ◎ | 中 | 物理移動が必須。最強。iOSも読取可 |
| ★ QRコード | 同上、印刷したQRをカメラで読む | ◎ | 低 | NFC無し端末でも可。MVPはこれが有力 |
| ★ 歩数 | 加速度センサーで n 歩 歩く | ◎ | 中 | 手で振って偽装可能なのが弱点 |
| 計算問題 | 暗算を n 問連続正解（誤答でリセット） | ○ | 低 | 布団の中で解けてしまう |
| タイピング | 表示された文章を正確に書き写す | ○ | 低 | 難度調整しやすい。実装が最も楽 |
| 記憶ゲーム | 光る順番を記憶して再現 | ○ | 中 | ゲーム性が高く飽きにくい |
| シェイク | 端末を n 回振る | △ | 低 | 寝たままできる。単体では不十分 |
| 写真照合 | 登録した場所の写真を撮る（画像比較） | ◎ | 高 | 精度と誤判定が課題。将来機能 |
| バーコード | 洗面所の歯磨き粉のバーコードを読む | ◎ | 低 | QRの応用。印刷不要が利点 |

**推奨MVP構成**: タイピング or 計算（実装が容易・確実に動く） + QRコード（本命の覚醒効果）

### 4.3 不正防止（ここが本質。難度順）

| 抜け道 | 対策 | 難度 |
|---|---|---|
| ホームに戻る / 他アプリを開く | フォアグラウンドサービスで監視し、離脱を検知したら再度全画面表示 | 中 |
| 音量ボタンで消音 | 音量キーをインターセプト、またはアラーム音量を毎秒書き戻す | 中 |
| マナーモード/集中モード | Androidはアラーム音声チャンネルで突破可。**iOSは原則突破不可** | — |
| 通知を上スワイプで消す | 通知ではなく全画面Activityで起動する | 低 |
| アプリを強制終了（タスクキル） | 終了検知→即再起動。完全防止は不可能 | 高 |
| 機内モード | ローカル動作なので影響なし（設計としてオフライン前提） | 低 |
| 端末の電源を切る | **防げない。** 起動時に「不正終了」として記録し、ログに残す | — |
| アプリをアンインストール | 防げない。デバイス管理者権限で抑止する手はあるが過剰 | — |

> **設計方針の決め所**: 「完全に破れないシステム」は不可能。
> 目指すのは「**寝ぼけた頭では突破が面倒くさい**」レベル。心理的コストを上げるのが本質で、
> ここに過剰投資するとメンテ不能になる。**ログに残す（自分に嘘をつけない）** が費用対効果◎。

### 4.4 将来機能（MVP後）

- 統計ダッシュボード（週次の起床時刻ブレ、スヌーズ回数推移）
- ストリーク/実績バッジなどのゲーミフィケーション
- ペナルティ連携（失敗したら指定のSNSに自動投稿、送金など）
- 睡眠サイクル検知によるスマート起床（±30分の最適タイミングで鳴らす）
- 天気/カレンダー連携（雨なら10分早く鳴らす）
- 起床チャレンジの共有（友人と競う）
- 目覚まし音のカスタム、徐々に音量が上がるフェードイン

## 5. 非機能要件

| 項目 | 要求 |
|---|---|
| **信頼性** | **最優先**。「鳴らなかった」は致命的欠陥。1度でも起きると信用を失い使われなくなる |
| オフライン動作 | 完全オフラインで機能すること（サーバー依存はアラームの信頼性を落とす） |
| 起動速度 | 発火からアラーム画面表示まで 1秒以内 |
| 電池消費 | 待機時はほぼゼロ（OSのアラームスケジューラに委譲する設計） |
| 誤操作耐性 | 寝起きの雑な操作でも壊れない。タスク中の誤タップでリセットしすぎない |
| 視認性 | 暗い部屋・寝起きの目でも読める大きな文字とコントラスト。画面は徐々に明るく |
| データ保持 | 端末ローカル保存。OSアップデート/再起動でアラーム設定が消えないこと |
| プライバシー | 個人データは端末外に出さない |

## 6. プラットフォーム制約（重要）

### Android
- `AlarmManager.setAlarmClock()` で Doze モードを突破し、正確な時刻に発火可能
- フルスクリーンIntent + フォアグラウンドサービスで「純正時計アプリ同等」のアラームが作れる
- Android 14以降は `USE_EXACT_ALARM` / `SCHEDULE_EXACT_ALARM` 権限の宣言が必要
- 一部メーカー（Xiaomi/OPPO/Huawei等）の独自省電力機能でキルされる問題あり → 自動起動許可の案内が必要
- **結論: やりたいことがほぼ全部できる**

### iOS
- ローカル通知の音は**最長30秒**。連続で鳴らし続けられない（通知を連打する回避策はある）
- サイレントスイッチ/集中モードを突破するには **Critical Alerts entitlement** が必要（Appleの個別承認制、医療用途以外はほぼ通らない）
- バックグラウンドでの任意コード実行が厳しく制限される
- 回避策: 無音の音声をバックグラウンド再生し続けてアプリを生かす手法（実績あるが電池を食う／Appleの審査リスク）
- フルスクリーン起動の概念がない（通知タップで初めてアプリが開く）
- **結論: 「絶対に止められないアラーム」は原理的に作れない。妥協が必要**

### PWA / Web
- 正確な時刻でのローカル発火手段が無い（Service Worker のタイマーは信頼できない）
- Web Push はサーバーが必要 + 音が鳴らせない
- **結論: 本番のアラームには不向き。UI/タスクロジックの試作用には有効**

## 7. 決めるべき論点（← ここを一緒に固めたい）

1. **対象端末**: iPhone / Android / 両方 — これで技術スタックがほぼ決まる
2. **スコープ**: 自分専用ツール / 身内配布 / ストア公開
3. **解除タスク**: MVPでどれを実装するか（実装容易な1つ + 本命の1つ、を推奨）
4. **スヌーズ**: 完全禁止 / 回数制限つき / タスクが重くなる方式
5. **不正防止の強度**: どこまでやるか（ログに残すだけ 〜 徹底ブロック）
6. **開発環境**: Mac の有無（iOS実機ビルドの可否に直結）
